# 사진 촬영·확인 대기 2단계 Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans. User approved cancel fix first, then phase 2.

**Goal:** 취소 시 홈·목록으로 돌아오고, 대기 사진을 쉽게 지우며 다시 찍기·업로드 상태·재시도를 신뢰할 수 있게 한다.
**Architecture:** 실제 이동을 가진 개발용 호스트, 공유 대기 사진 행·상세, 사진별 활성 업로드와 저장 가능한 업로드 체크포인트를 사용한다. 기존 POST /photos → PUT → POST /complete API를 유지한다.
**Tech Stack:** SwiftUI, XCTest/XCUITest, iOS 17+.
**Spec:** Downloads/ux-improvements-2026-10-29.md 1-3, 사용자 승인 2단계 및 취소 버그 보고.

## Global Constraints
- 실제 사용자 사진·URL·토큰은 커밋·로그에 남기지 않는다.
- 서버의 complete는 멱등이다. 서버 사진 DELETE API는 없다. 이 단계 삭제는 기기 대기 사진 삭제로 한정하고 UI에 범위를 알린다.
- 사진 삭제와 기록 확인 완료를 구분해 저장된 기록의 서버 사진을 지우지 않는다.
- 취소/다시 찍기/삭제로 취소된 작업이 화면을 나중에 닫거나 사진을 되살리면 안 된다.

## Review Focus
- 루트에 단독으로 열린 개발 화면도 취소할 수 있어야 한다.
- 취소·저장 실패 시 확인 대기 사진은 남고, 확인 성공 때만 제거한다.
- 진행 중·대기 중·실패·확인 가능 상태를 사진별로 구분한다.
- 삭제·다시 찍기는 업로드 작업을 취소하며, 늦은 응답이 사진을 복구하지 않는다.
- 완료 통보 재시도는 같은 서버 photo_id를 사용한다. 발급 응답 자체를 잃은 경우의 완전한 멱등성은 서버 지원이 필요하다.

## 결과와 결정 (2026-10-29)
- 취소 UI 회귀를 수정 전 재현하고, 실제 홈 위 시트로 열어 취소 시 홈으로 복귀하도록 수정했다.
- DEBUG 음식 인식 예시는 미리보기임을 표시하고 실제 저장을 막는다. 기본 앱의 저장 동작은 유지한다.
- 목록과 하루 마무리에 사진별 상태·삭제 버튼·밀어서 삭제, 상세에 사진·재시도·삭제를 연결했다. 재확인은 취소 버튼이 명시되는 alert를 사용한다.
- 사진 ID와 전송 체크포인트는 보호된 기기 저장소에만 보관한다. 완료 통보 재시도는 같은 서버 사진 ID를 사용한다. 발급 응답 자체를 잃은 경우와 서버 저장 성공 응답을 잃는 경우의 완전한 멱등성은 서버 지원이 필요하다.
- 사진 삭제는 원본을 임시 보관하고 index 변경이 성공한 뒤 정리한다. index 저장 실패·중간 종료 후에는 사진을 복구한다.
- 기록 저장 후 사진 정리 실패는 완료 표시를 별도 보관해 재시작 후에도 중복 기록 생성으로 이어지지 않도록 한다. 이 경우 상세에서 기기 사진 정리만 재시도한다.
- 늦게 로드된 앨범 사진은 업로드 시작·새 선택으로 무효화하며, 재촬영 시 기존 닫기 타이머를 먼저 무효화한다.
- 서버 사진 DELETE API가 없으므로 서버 원본은 이 단계에서 삭제하지 않는다. UI에 그 범위를 표시한다.
- 독립 리뷰에서 지적한 4개 Important 문제를 회귀 테스트와 함께 수정했다.
- 실제 인증 서버/R2 왕복, 실기기 카메라, iOS 17 런타임은 이 환경에서 검증하지 못했다. UI 실행은 iOS 26.5 시뮬레이터이며 예시 사진은 실제 사용자 저장소와 분리한다.
- 최종 검증: XCTest 35개와 XCUITest 6개가 모두 통과했다. 앱·위젯의 generic iOS Simulator 빌드와 git diff --check도 통과했다. 새 업로드 코드의 Sendable 경고는 정리했고, 기존 다른 파일의 actor isolation 경고는 남아 있다.
