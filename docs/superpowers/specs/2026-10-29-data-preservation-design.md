# 5단계: 계정별 데이터 보존과 복원

사용자가 기존 단계 계획의 다음 단계 진행을 승인했다. PR #78의 1~4단계 코드는 유지하고, 403c3c8에서 분기한 feat/data-preservation에서 구현한다. 운영 DB·서버 설정·main 병합·TestFlight 배포는 실행하지 않는다.

## 목표
- 하루 마무리·기록만 저장·연속 완성일·꿀단지·쉬어가기 상태를 같은 계정의 서버에 저장하고 새 설치/기기에서 복원한다.
- 서버에 업로드된 확인 대기 사진의 촬영 시각·분류·확인/숨김 상태를 복원한다. 업로드 전 파일은 기기에만 존재하며 이 한계를 표시한다.
- 오프라인 변경과 응답 유실 재전송이 중복 보상·사진 재등장·오래된 응답 덮어쓰기를 만들지 않게 한다.
- 계정 전환/로그아웃 시 이전 계정의 기록과 업로드가 새 계정으로 넘어가지 않게 한다.

## 방법과 범위
서버 단일 상태와 멱등 변경 명령을 사용한다. 서버는 사용자별 잠금 안에서 명령 ID를 처리하고 상태/확인된 명령 ID를 반환한다. iOS는 기기에 먼저 저장한 변경 큐를 보낸 뒤 확인된 명령만 제거하고, 응답을 기다리며 생긴 새 변경은 다시 적용한다.

전체 스냅샷을 무조건 덮어쓰는 방법은 동시 기기의 기록이 사라지고 보상이 중복될 수 있어 채택하지 않았다. iCloud만 쓰는 방법은 기존 인증/API와 서버 사진을 별도로 관리하게 되어 채택하지 않았다.

## 하루 마무리 계약
- GET /v1/progress: 현재 계정 상태와 revision.
- POST /v1/progress/sync: 선택 legacy_state와 operations(최대 100개). 응답은 revision, state, acknowledged_operations.
- 명령: close_day(day, record_only), start_rest(day, end, reason), end_rest(day), apply_honeypots. 명령마다 UUID id가 있다. 동일 ID/내용 재전송은 한 번 처리하고, ID를 다른 내용으로 재사용하면 409다.
- 상태: closed_days, record_only_days, honeypot_saved_days, honeypots(0~2), rest(reason/start/end), last_honeypot_use. 날짜는 한국 시간 yyyy-MM-dd, 쉬어가기 reason은 기존 iOS 값 resting/unwell/noSensor.
- 같은 날 마무리는 한 번만 보상한다. 기록만 저장을 나중에 완성으로 바꾸면 완성으로 유지한다. 꿀단지의 7일·최대 2개·정오 유예·연속 계산 규칙을 유지한다.
- 첫 기존 데이터 가져오기는 상태/잔여 꿀단지를 보존한다. 서버 상태가 이미 있으면 완성 날짜와 보호 날짜는 합치고, 꿀단지 잔액과 현재 쉬어가기는 서버 값을 유지한다. 두 기기의 잔액을 합산하지 않는다.
- 쉬어가기 변경 충돌은 서버가 받은 명령 순서로 처리한다. 오프라인에서 오래된 명령을 나중에 보내면 그 의도가 마지막으로 적용될 수 있다.
- Flyway로 사용자 상태/처리 명령 테이블을 추가하고 app_user 삭제와 함께 cascade한다.

## 사진 계약
- POST /v1/photos의 기존 필드는 유지하며 captured_at과 client_id를 선택 필드로 추가한다. 같은 계정/client_id 재시도는 같은 사진 ID와 새 업로드 주소를 반환한다.
- GET /v1/photos?unconfirmed=true&cursor=&limit= : 업로드 완료·미확인·미숨김 사진의 메타데이터를 cursor로 반환한다. 보기 URL/객체 키를 목록에 포함하지 않는다.
- GET /v1/photos/{id}: 소유자에게 상태·촬영 시각·분류·client_id·confirmed·dismissed를 반환한다.
- PATCH /v1/photos/{id}/metadata: 이전 앱이 업로드한 사진의 누락된 촬영 시각/client_id를 보완한다.
- POST /v1/photos/{id}/dismiss: 대기 목록에서 멱등으로 숨긴다. R2 원본은 삭제하지 않는다.
- 사진과 연결된 음식 기록 저장 시 같은 트랜잭션에서 확인 처리한다. 기록을 나중에 지워도 사진이 대기 목록으로 되살아나지 않는다. 기존 연결 사진은 마이그레이션에서 확인 처리한다. 다른 사용자 사진은 연결/조회/숨김 불가.
- 사진 완료/숨김/확인은 행 잠금으로 직렬화한다. 숨긴 업로드의 늦은 완료 요청은 다시 대기 사진을 만들지 않는다.
- iOS는 전체 목록 조회 성공 후 추가하고, 누락된 기존 사진은 개별 상태를 확인해 확인/숨김이 확정된 경우만 정리한다. 부분 조회·실패·계정 변경은 파일 삭제 근거가 되지 않는다.
- 복원 사진은 보기 URL을 메모리에서 받아 썸네일/원본을 표시한다. 원본이 기기에 없다고 재업로드하지 않는다.

## 계정 분리와 기존 자료
- 서버 권한은 JWT 검증 주체로만 결정한다. 앱 JWT sub는 로컬 캐시 폴더를 고르는 용도이며 권한 부여로 사용하지 않는다.
- 완료 상태·사진 폴더·변경 큐와 로컬 이름/평소 인슐린 설정을 계정별로 분리한다. 온보딩 완료는 기기 설정으로 유지한다.
- 로그아웃은 진행 중 동기화를 취소하고 표시/위젯을 비우되 계정별 파일은 보존한다. 재로그인 시 같은 계정 캐시를 이어 쓴다. 계정 삭제는 해당 계정 자료를 지운다.
- 업그레이드 시작 시 기존 토큰의 사용자가 확인되면 그 계정으로 기존 캐시를 이전한다. 소유자를 알 수 없는 예전 캐시는 자동 업로드하지 않고 보존하며, 설정에서 사용자가 현재 계정으로 가져오도록 한다.
- 동기화 요청은 시작 계정과 세대를 확인하고, 이전 계정 응답은 새 계정에 적용하지 않는다. 404/오프라인/이전 서버에서는 로컬 변경을 유지한다.

## 사용자에게 보이는 상태
설정의 기록 백업에서 서버 저장 여부·재시도·기존 기기 기록 가져오기를 제공한다. 하루 마무리와 사진 입력은 통신이 끊겨도 계속 기기에 저장된다. '업로드 전 사진은 이 기기에만 남아요'를 안내한다.

## 검증
PostgreSQL Testcontainers에서 실제 인증·스키마·HTTP·사용자 격리·재전송/동시 처리·계정 삭제를 검사한다. iOS는 영속 큐 재실행·늦은 응답·다른 계정·부분 페이지·숨김 재시도·원격 사진 복원을 검사한다. 외부 저장소/네트워크만 경계에서 대체하고 테스트 자료는 합성한다.
